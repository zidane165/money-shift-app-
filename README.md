
# 所持金・シフト管理アプリ（未来残高シミュレーター）

大学生の給料日ズレによる資金ショートを防ぎ、365日先までの未来残高と「130万円の壁」を可視化する、給料日・シフト・支出連動型 未来残高予測アプリ収支管理アプリケーションである。

---

## 1. アプリ概要

* **アプリ名**: 未来残高シミュレーター
* **ターゲット**: 大学生・アルバイト・(フリーター)
* **主要目的**: 複数アルバイトの給料振込日のズレや突発的な出費による給料日前の資金ショートを防止し、安心して生活・推し活・旅行等の計画を立てられる環境を提供する。

---

## 2. アプリ概要と開発背景

### 課題意識と開発背景
大学生やフリーターは、複数のアルバイトを掛け持ちすることが多く、バイト先ごとに「15日払い」「26日払い」といった給料日や締め日のタイムラグが存在する。このタイムラグにより、手元の現金と実際の収支に誤認が生じ、クレジットカードの引き落とし日や固定費支払い時に給料前でお金が足りなくなるかもという問題、また、どのくらい働く必要があるのかをカレンダー等で確認したりと煩わしい問題が発生していた。そして、年末における扶養の壁超過の懸念も年末ぎりぎりになって慌てるといった大きな負担となっていた。

### MVP要件
本アプリは上記課題を解決するため、以下の機能をコアMVPとして定義・実装した。 
1. **労働基準法に準拠した給与自動予測**: アルバイトごとの時給・締め日・給料日ルールとシフト入力から見込み給与を自動計算する機能。
2. **365日未来残高シミュレーションと赤字警告**: 現在の実残高・未来の給料・予定出費を日別で計算し、残高がマイナスに転落する日を赤色で強調警告する機能。
3. **扶養枠の進捗表示**: 年間累計収入と上限までの残額をゲージで可視化する機能。

### 開発工程
本アプリの開発は、段階的な品質向上を目指し以下の5つのフェーズで実施した。

* **フェーズ1:基本UIとデータ入力の土台構築**
  * `Scaffold` および `BottomNavigationBar` による2タブ構造の画面骨組みを定義した。
  * `showModalBottomSheet` による収支入力UIを構築し、`ListView.builder` による履歴表示と `LinearProgressIndicator` を用いた「130万円の壁」ゲージ連動を実装した。
* **フェーズ2:マスター設定とデータモデルの設計**
  * アルバイト先指標（時給、締め日、給料日、テーマカラー）を管理する `Job` クラスを設計した。
  * 収支データ（`ExpenseRecord` 等）に `DateTime` 型を持たせ、発生日・金額・項目を一元管理するデータ構造を定義した。
* **フェーズ3:シフト入力と労働基準法自動計算ロジックの実装**
  * `showTimePicker` による直感的な時間入力UIを構築した。
  * 労働基準法（6時間超で45分、8時間超で1時間の休憩控除）に則った実労働時間および見込み給与の自動計算ロジックを実装した。また、当日の早上がりなどの勤怠の急な変更に対応する `Slider` UIを追加した。
* **フェーズ4:カレンダー構築と未来残高シミュレーションアルゴリズム**
  * `table_calendar` パッケージを採用し、日付選択で詳細（Daily View）が開くカレンダー画面を構築した。
  * シフトデータとバイト先ルールを掛け合わせて未来の入金日へ給与を自動配置し、現在の所持金から日別の収支を365日後までループ計算してマイナス転落日を赤字（`Colors.red`）描画するアルゴリズムを完成させた。
* **フェーズ5:効率化・データ永続化・Webデプロイ準備:**
  * 固定費の繰り返し登録機能および月初めの休日ズレ調整用 `AlertDialog` アラートを実装した。
  * `SharedPreferences` と JSONシリアライズを用いたローカルデータ永続化を行った。

## 3. 主要機能

### 1:カレンダー画面（未来残高シミュレーション＆資金ショート赤字警告）
* **未来残高の自動マッピング**: 各日付マスに「その日終了時点での予想預金残高」を表示し、未来の給料予定日には入金予定額を自動配置する。
* **資金ショート赤字警告**: 現在の所持金・未来の収入・固定費や予定出費を日別で計算し、残高が0円未満（マイナス）になる日の文字色を自動で赤色（`Colors.red`）へ変更して警告する。

* **Daily View（日別詳細導線）**: 日付をタップすることで、その日の具体出費（イベント代・日常出費など）の確認および新規記録をその場で行える。

### 2:シフト入力＆労働基準法に沿った自動給料計算
* **勤務時間からの自動給与算出**: 開始・終了時間を選ぶだけで、労働基準法（6時間超で45分、8時間超で1時間控除）に基づく実労働時間を自動算出し、バイト先ごとの時給と掛け合わせて見込み収入を計算する。
* **当日勤怠修正スライダー**: 直感的なスライダー操作により、急な早上がりや残業が発生した際も即座に勤務時間を微調整できる。
* **マルチバイト先マスター設定**: 複数のバイト先（時給・締め日・給料日・カラー設定）を保持し、それぞれのルールに基づいた給与計算に対応する。

## 5. 技術的な工夫・チャレンジした点

### 1:労働基準法に準拠した給与自動計算ロジックのモジュール化
勤務の開始・終了時間（`TimeOfDay`）から実労働時間を算出する際、労働基準法（6時間超で45分、8時間超で60分の休憩自動控除）に基づいた判定アルゴリズムを構築した。また、UI（`onPressed` イベント等）の中にロジックを直接記述するのではなく、引数として時間や時給を受け取って計算結果（整数型の金額）を返す独立した関数（`salaryCalculation`）として外出し・モジュール化することで、コードの可読性と保守性を飛躍的に向上させた。

### 2:締め日・給料日の月跨ぎ・翌月払い判定アルゴリズム
「20日締め・翌月10日払い」や「末日締め・翌月25日払い」など、バイト先ごとに異なる複雑な給料体系に対応する判定ロジック（`calculatePayDay`）を自作した。シフト日と締め日の比較に加え、給料日と締め日の大小関係から振込月（`targetMonth`）の加算処理を行った。Dartの `DateTime` が月数の繰り上げ（13月→翌年1月）を自動補正する仕様を活用し、年跨ぎでも処理が破綻しない堅牢な設計とした。

### 3:365日未来残高シミュレーションと `table_calendar` の表示制御
現在の実残高を起点とし、今日から365日後まで1日ずつループを回して「その日の支出の引き算」と「給料日の収入の足し算」を時系列順に追う予測エンジン（`getShortageDays`）を構築した。残高が0円未満（マイナス）となった日付を抽出し、`table_calendar` パッケージの `holidayPredicate`（祝日判定機能）と `calendarStyle` を応用して、該当するカレンダーのマス目を動的に赤色描画して注意を促す仕組みを実現した。

### 4:`SharedPreferences` と JSONシリアライズによる複数オブジェクトの永続化
ローカル保存ライブラリである `SharedPreferences` はプリミティブ型（`int` や `String` 等）しか直接保存できない制約があったのでこれを克服するため、カスタムクラス（`ShiftRecord`, `Job`, `ExpenseRecord`, `Subscription`）内に `toJson()` および `fromJson()` メソッドを定義した。`DateTime` 型を ISO-8601 形式の文字列へ変換して `jsonEncode` / `jsonDecode` を通すことで、構造化されたオブジェクトリスト全体の永続化および復元を可能にした。

## 6. 苦労した点と学び・今後の課題

### 苦労した点と解決方法

#### 1:モーダル・ダイアログ内における状態管理とリアルタイム画面更新
`showModalBottomSheet` や `AlertDialog` 内でドロップダウン選択や入力変更を行った際、親画面の `setState` ではモーダル内のUIが更新されない（表示が切り替わらない）現象に直面した。
* **解決策**: モーダル内部のコンテンツを `StatefulBuilder` で包み込み、専用のスコープ更新関数（`setModalState` や `setDialogState`）を呼び出すことで、モーダルを開いたまま局所的にリアルタイムな画面更新を行う構造を理解・実装した。

#### 2:リスト絞り込み表示時の安全なスワイプ削除処理
カレンダー下の絞り込みリスト（`selectedRecords`）において、表示順のインデックス（`index`）をもとに要素を削除しようとした際、大元の全体リスト（`records`）のインデックスとズレが生じ、無関係な日付のデータが削除されてしまう危険性があった。
* **解決策**: `Dismissible` ウィジェットを使用する際、インデックス指定（`removeAt`）ではなく、オブジェクト固有のハッシュコード（`hashCode`）をキーとして指定し、データの実体そのものを特定して削除（`records.remove(record)`）する安全な実装に改善した。

#### 3:直感的な入力UIへの改善（15分刻みドラムロールピッカー）
従来の時計ダイヤル式タイムピッカー（`showTimePicker`）はタップ回数が多く、頻繁に行うシフト入力において操作ストレスが大きいという課題があった。
* **解決策**: `flutter/cupertino.dart` の `CupertinoDatePicker` を導入し、15分刻み（`minuteInterval: 15`）でスワイプ操作できるドラムロール式ピッカー関数（`_showSpinnerTimePicker`）へと刷新した。エラーを防ぐため、初期値の分を15の倍数に丸める前処理も実装した。

### 学び
* **アーキテクチャ・責任分離の重要性**: 入力（UI）、データモデル（クラス）、計算（ロジック）を適切に分離・モジュール化することで、バグの特定が容易になり可読性が劇的に高まることを実感した。
* **スコープと生存期間の理解**: ウィジェットツリーにおける変数のスコープ（`build` メソッド内での再計算と状態保存用変数の切り分け）や、非同期処理（`async/await`）を伴うローカルデータ通信の仕組みを深く習得した。

### 今後の課題・展望
* **クラウドデータベース（Firebase Firestore）連携**: 現在は `SharedPreferences` によるローカル保存のためブラウザのキャッシュ消去でデータが初期化される。今後は Firebase 連携などを導入し、複数端末間でのリアルタイム同期と安全なバックアップを実現したい。
* **Firebase Hosting によるWeb公開**: `flutter build web` によるビルド成果物を Firebase Hosting や GitHub Pages にアップロードし、実際のユーザーや採用担当者がブラウザからワンタップで試せる環境をデプロイする予定である。
